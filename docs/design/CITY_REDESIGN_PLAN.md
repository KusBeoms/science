# 도심 재설계: 실제 도로 위계 + JSON 데이터 + 브라우저 에디터

## Context
지금 도심은 축 정렬 선분(`CityRoad`)과 사람이 적은 좌표, 시드 생성기(`city-w3/w7.ts`)가 섞여 있다. 도로 위계가 없고 대각선·곡선·입체교차로를 표현하지 못한다. 길찾기 그래프(`citygraph.ts`)와 장소(`places.ts`)도 좌표를 따로 적어 두었다.
목표는 첨부 이미지처럼 **고속·국도 / 주간선 / 보조간선 / 집산 / 국지** 5단계 도로망을 가진 새 도심을 **JSON 하나**로 정의하고, 그 JSON을 **브라우저 에디터**로 고치는 것이다. 건물·가로등·나무 등 기존 로우폴리 에셋은 그대로 재활용한다.
사용자 결정: 고정물 위치까지 전부 새로 배치 / 에디터는 단독 웹 페이지 / JSON이 있으면 새 도심, 없으면 기존 코드.

## 1. 도시 구조 구상 (이미지 → 규칙)
이미지의 색을 도로 5단계로 매긴다.

| 등급 | 이미지 | 폭(차선) | 속도 | 보도 | 교차 처리 |
|---|---|---|---|---|---|
| 고속·국도 `expressway` | 주황 | 4~6차선+중앙분리대 | 빠름 | 없음 | 입체교차(IC/JCT), 도시 외곽으로 연결 |
| 주간선 `arterial1` | 노랑 | 4~6차선 | 중간 | 넓음 | 신호 교차로, 일부 고가 |
| 보조간선 `arterial2` | 초록 굵은 선 | 2~4차선 | 중간 | 있음 | 신호·로터리 |
| 집산 `collector` | 초록 가는 선 | 2차선 | 느림 | 있음 | 국지도로를 모아 간선에 연결 |
| 국지 `local` | 보라 | 1~2차선 | 매우 느림 | 좁음 | 블록 안 격자, 막다른 길 허용 |

배치 원칙 (이미지에서 읽은 것):
- 고속은 도시 윤곽을 가로지르는 3~4개 큰 곡선이다. 교점마다 입체교차로가 있다. 도심 한복판은 피하고 가장자리로 지난다.
- 주간선은 도시 윤곽 밖으로 뻗는 방사형이고, 중앙에서 만난다.
- 보조간선·집산은 지역(블록 군)을 둘러싸는 고리 모양이다. 국지 격자는 그 고리 안에만 채운다.
- 같은 지역 안 국지 격자는 방향이 일정하고, 지역마다 방향이 다르다(이미지의 서쪽·중앙·동쪽 격자).
- 막다른 길은 국지에서만 허용한다.

고정물(전부 JSON의 `anchors`로 정의, 에디터에서 이동 가능):
경기장(105×68 구장+스탠드), 포탈 광장(12기둥), 다리 접속로(= 도시 윤곽의 `BRIDGE_ENDS`와 일치해야 함), 스폰·사과 기지, 사과 시선 축(정북 ±8°, 고도 8°) 보호구역, 산악도로 시작점. 에디터의 검증이 이 제약을 항상 검사한다.

## 2. JSON 스키마 (`client/public/data/city.json`)
```
{ version, seed, bounds:{polygon:[[x,z]...]},        // 도심 땅 윤곽(기존 outline.ts의 CITY_POLY 사용)
  roads:[{id, cls, pts:[[x,z]...], curve:'poly|spline', grade:0|1|-1, name?}],  // 중심선, 폭·보도는 등급표에서
  nodes:[{id, x, z, kind:'signal|roundabout|interchange|plain', roads:[ids]}],  // 교차로(대부분 자동 추출, 덮어쓰기 가능)
  zones:[{id, poly, use:'highrise|commercial|apartment|house|park|industrial|civic', density}], // 블록 용도
  parcels:[{road, side, t0, t1, depth, use}]|auto,     // 도로변 필지, 비어 있으면 zones에서 자동 분할
  buildings:[{id, legacyId?, spec:CityBuilding필드+rot}], // 확정(bake)된 건물. 아이디 고정 → 저장 데이터 보호
  anchors:[{id, kind:'stadium|portal|spawn|bridge|landmark|park|fun', x,z,rot, ref:에셋id}],
  props:{rules} }
```
- 건물 아이디는 JSON에 고정 저장한다. 생성기를 다시 돌려도 아이디가 바뀌지 않는다(기존 `S.props` 구매 기록 보호). 옛 아이디는 `legacyId`로 연결한다.
- 로드 시 검증(스키마, 도로 연결성, 막힌 문 등)을 한 곳에서 수행한다.

## 3. 에셋 재활용 방식
| 기존 에셋 | 재활용 | 필요한 변화 |
|---|---|---|
| 건물 `makeBuilding / makeHighrise / makeHouse / shopFront` (`render/city/*`) | JSON `buildings.spec`(= 기존 `CityBuilding`)를 그대로 입력 | `CityBuilding`에 회전 `rot` 추가. 대각 도로변 건물은 도로 접선 방향으로 회전. 충돌은 회전 사각형을 AABB 여러 조각으로 등록 |
| 랜드마크·경기장·대관람차 등 (`landmarks*.ts`) | `anchors`에서 id로 호출 | 위치·회전을 JSON에서 받도록 `index.ts`의 하드코딩 좌표 제거 |
| 고가·입체교차 (`overpass*.ts`, `core/deck.ts`) | `grade:1` 도로와 `interchange` 노드가 사용 | 지금은 축 정렬 `VIADUCTS`뿐 → 데크를 **폴리라인 중심선 + 높이 프로파일**로 일반화 |
| 도로면 (`layout.ts` `surfaceAt` 1u 셀 색칠) | 방식 유지, 입력만 교체 | 선분 거리장(공간 해시)으로 도로·보도·중앙선을 칠함. 대각·곡선 지원 |
| 횡단보도·신호 (`crosswalks.ts`) | `signal` 노드마다 생성 | 교차 각도·도로 폭을 노드에서 계산 |
| 가로등·나무·벤치 (`props.ts`, `planProps`) | 등급별 규칙(간격·열)로 도로 가장자리를 따라 인스턴싱 | 하드코딩 좌표 목록 제거 |
| 프리미티브·병합·팔레트 (`lowpoly/*`, `instancedChunks`) | 변경 없음 | — |
| 길찾기 `citygraph.ts` | 도로 그래프에서 **자동 생성**(보도 레인 오프셋, 20u마다 노드) | 손으로 쓴 `link([...])` 제거. `buildingRoutes`는 재사용 |
| 주차·경찰·택시·폰 지도·`PLACES` | 모두 새 도로·앵커 데이터를 읽음 | 폰 지도는 JSON을 그리고, `PLACES`는 `anchors`/건물 문으로 계산 |

## 4. 도심 만드는 흐름
1. **도로망 작성**: 에디터로 고속→주간선→보조간선 순서로 큰 뼈대를 그리고, 집산·국지로 채운다. 첫 버전은 이미지를 본떠 내가 JSON을 손으로 작성한다.
2. **교차 처리**: 자동으로 교차점을 노드화하고 종류를 추천(고속×주간선=입체교차, 간선끼리=신호, 국지=일반).
3. **블록·용도**: 도로로 둘러싸인 면(블록)을 자동 추출하고 지역별 용도를 칠한다. 중심은 고층, 가장자리로 갈수록 아파트→주택.
4. **필지·건물**: 도로변 필지 분할 후 용도에 맞는 `CityBuilding` 스펙을 시드로 만들어 `buildings`에 확정 저장한다.
5. **게임 연결**: 부팅 때 JSON을 읽어 지형 평탄화·충돌·그래프·렌더가 모두 같은 데이터를 쓴다.

## 5. 부팅 시 JSON 로딩
- 현재 데이터 모듈은 import 순간 계산되고(`CITY_BUILDINGS`, `CITY_GRAPH` 등), `tsc`에 `resolveJsonModule`도 없다.
- 방식: `main.ts`가 먼저 `fetch('data/city.json')`로 읽고, 있으면 `CITY_DATA` 싱글턴에 넣은 뒤 **게임 모듈을 동적 `import()`**한다. 파일이 없거나 검증 실패면 기존 코드 경로를 그대로 쓴다.
- 데이터 모듈은 `CITY_DATA`가 있으면 JSON에서, 없으면 기존 값을 내보낸다(전환 스위치는 `data/city-source.ts` 한 곳).
- `public/data/`는 nginx와 테스트 서버 모두 정적으로 서빙한다. `nginx.conf`에 `.json` 캐시 정책(`no-cache`)만 추가한다.

## 6. 에디터 (`client/public/editor.html` + `client/src/editor/*.ts`)
단독 페이지, 서버 없이 동작. tsc가 `js/editor/*`로 컴파일한다. 파일마다 500줄 이하.
- 2D 캔버스: 윤곽·기존 도시 배경, 확대·이동, 격자 스냅, 도로 끝점·교차점 스냅.
- 도구: 도로 그리기(등급 선택), 정점 이동·삽입·삭제, 곡선/직선 전환, 고가/지하 토글, 노드 종류 변경, 구역 칠하기(다각형), 앵커 배치·회전, 건물 수동 추가·삭제.
- 자동 기능: "필지·건물 자동 채우기"(구역 단위), 막다른 길·고립 도로 표시.
- 검증 패널: 도로 연결성, 사과 시선 축 침범, 건물 겹침·문 막힘, 다리 접속 일치, 삼각형 예산 추정, 아이디 중복.
- 3D 미리보기: 에셋 샘플(건물·가로등)을 three.js 소창으로 확인. "게임에서 보기"는 `index.html?debug=1&city=local`(localStorage의 JSON)로 연다.
- 입출력: JSON 다운로드·불러오기, localStorage 자동 저장, 실행 취소/다시 실행.
- 에디터 코어(스냅·스키마·검증)는 게임과 같은 `data/city-schema.ts`·`city-validate.ts`를 공유한다.

## 8. 위험과 대응
- **대각 건물 충돌**: `addSolid`는 AABB뿐이다. 회전 건물은 AABB 조각으로 근사하고, 에디터는 회전을 15° 단위로 제한한다.
- **삼각형 예산**: 스폰 시야 110k 한도를 에디터 검증이 추정한다. 이미 112k라서 새 도심 시작점에서 줄여야 한다.
- **저장 호환**: 건물 아이디를 JSON에 고정하고 `legacyId`로 옛 구매 기록을 연결한다. 연결 못한 기록은 환불 처리 여부를 구현 전에 사용자에게 확인한다.
- **하드코딩 테스트**: `crowd/downtown/overpass/phone/city.spec`가 도심 좌표를 직접 쓴다. 앵커·JSON에서 좌표를 읽도록 바꾸고, 기존 코드 경로용 테스트는 폴백 모드에서 계속 돌린다.
- **진행 중인 W7 작업**: CITY_DENSITY·RURAL 에이전트가 레이트 리밋으로 중단됐고 `city-w7.ts` 등이 미완 상태다. 새 도심이 이를 대체하므로, 구현 전에 W7 도심 쪽 변경을 폐기·보존할지 정리한다(시골 섬 작업은 별개로 재개).
- **문서·정책**: 500줄 제한, `docs/README.md`·`tech/` 갱신, `COORDINATION.md` 기록, 마일스톤마다 커밋.

## 8-2. 추가 요구 6가지 (도심과 함께 해결)

### ① 아파트 주차 차량은 모두 탈 수 있게, 장식 차 없음
- 현황: 아파트 주차장(`render/city/downtown.ts` `parking`), 경기장 주차장(`w7-features.ts`), 상점 앞 전시 차(`shopstreet.ts`)는 상자 모양 장식이라 탈 수 없다. 탈 수 있는 차는 도로변 26대뿐이다(`systems/vehicle.ts` `planSpots`, `spawnVeh`).
- 계획: JSON에 `parking` 칸(좌표·방향·소속 건물)을 정의한다. 장식 차 생성 코드는 삭제한다.
  - 주차 칸의 차는 전부 `spawnVeh`로 만든 실제 차량이다. 탈 수 있고 충돌이 있다.
  - 전부 한꺼번에 만들면 무겁다. **플레이어 근처(약 90u) 칸만 차를 만들고, 멀어지면 제거한다.** 칸마다 차종·색·점유 여부는 시드로 고정해 다시 와도 같다.
  - 도난·시승은 지금처럼 `takeCar`, 비운 칸은 60초 뒤 다시 채운다.
  - `addDynSolid`가 전체 순회라서(O(n)) 근처 차만 등록하도록 바꾸고, 필요하면 격자 해시로 개선한다.
  - 상점 전시 차는 구매 가능한 실제 차로 바꾸거나 제거한다.

### ② 도로 이음새를 자연스럽게
- 현황 문제: 교차점에서 도로가 선분 순서에 따라 보행로·아스팔트로 갈리고, 중앙선이 일부 도로에만 있으며, 보도 모서리에 연석이 없고, 고가 경사로·다리 접속은 따로 붙인 데칼이라 색이 끊긴다.
- 계획: 도로를 **하나의 거리장·하나의 메시 생성기**로 통일한다.
  - 교차로는 노드에서 하나의 포장면(코너 반경 포함)으로 만든다. 교차점 내부에는 차선·중앙선을 그리지 않는다.
  - 등급이 높은 도로가 낮은 도로를 이긴다. 중앙선·차선·정지선·횡단보도는 같은 규칙에서 나온다.
  - 보도는 도로 가장자리 오프셋에서 만들고 코너를 둥글게 처리한다. 연석 높이 차이는 시각 줄무늬로 표현한다.
  - 도로 끝(도시 경계, 다리, 산악도로, 고속 출구)은 `bridge`/`mountain` 앵커에서 같은 폭·같은 높이로 이어 붙인다.
  - 검증: 에디터가 도로 끝점이 어디에도 안 닿는 곳, 폭·높이 불일치, 각도가 너무 급한 접합을 경고한다. E2E는 모든 도로 끝점을 걸어서 지나가 연속성을 확인한다.

### ③ 집 안은 도심과 이어진다 (순간이동 없음)
- 현황: E를 누르면 (1500,1500)의 별도 방을 만들고 순간이동한다(`game/interior.ts`, `render/interior.ts`, `core/terrain.ts`의 `setRoom`). 건물 창문은 불투명 상자, 문은 평면 그림이다.
- 계획:
  - **실제 위치 실내**: 방을 건물의 실제 좌표·회전에 만든다. 건물 외벽에 문 개구부(애니메이션 문)를 낸다. 문 근처에서 E를 누르면 문이 열리고 걸어 들어간다.
  - **근접 로딩**: 문에서 약 15u 안에 들어올 때만 실내를 만들고, 멀어지면 제거한다(`updateCityDetail`과 같은 거리 토글 패턴). 한 번에 최대 2~3채만 올린다.
  - **바깥이 어두워짐**: 플레이어가 건물 안 영역에 있으면 낮 조명·안개·하늘 밝기를 부드럽게 낮추는 "실내 어둠" 값을 쓴다. 실내 조명은 따뜻하게 유지한다. 나올 때 반대로 밝아진다.
  - **창문으로 실내가 보임**: 문 근처 건물은 창문 위치에 투명 유리와 실내 창가를 만든다. 멀리 있는 건물은 지금처럼 불 켜진 패널 그림으로 둔다. 실내를 안 만든 건물의 창문은 어두운 유리다.
  - **충돌**: `setRoom`은 모든 바깥 충돌을 교체하는 방식이라 폐기한다. 대신 외벽(문 개구부 제외)과 가구를 일반 충돌체로 건물에 붙이고, 실내가 올라올 때만 등록한다. 건물 안은 `G.inside` 대신 "건물 영역 안" 플래그로 판정한다.
  - `G.inside`에 의존하는 시스템(펫, 야생, 축구, 놀이, 경찰, 헬기, 주행)은 새 플래그로 옮긴다. 차를 문 앞에 대서 문이 막히는 검사(`nearbyExit`)는 사라지고, 문 개구부 앞 충돌만 본다.
  - 내부 종류가 많은(`ENTERABLES`, 8 랜드마크 + 건물 전부) 기존 가구 코드(`furnish*`)는 그대로 쓴다. 입력만 월드 좌표 + 회전으로 바꾼다.
  - 위험: 외벽에 구멍을 내면 건물 병합 메시가 깨진다. 문 주변 벽만 별도 조각으로 만든다. 실내 방은 대부분 작으므로 첫 단계는 "집·상점·사무실" 종류부터 하고, 랜드마크 실내(경기장 등)는 기존 방식을 잠시 유지한다. (이 단계는 사용자 확인 필요)

### ④ 도로 위에는 아무 것도 없음
- 현황: `planProps`의 손으로 쓴 가로등·나무·벤치와 `ROADS_W3` 가로등 루프는 도로 위 필터가 없고, 주차 칸도 도로 안(`w/2-1.7`)에 있다. 횡단보도 신호기 기둥도 도로 쪽이다.
- 계획:
  - 모든 소품은 **"도로 거리장" 필터를 공통으로 통과**해야 한다(도로 폭 + 연석 + 여유). 가로등·나무·벤치·신호기·간판은 보도·잔디띠 위에만 둔다.
  - 도로변 주차는 **주차대(별도 차선 띠)**로 만들어 주행 차로와 분리한다. 도로 위에는 달리는 차량만 있다.
  - 검증: 에디터의 검증과 E2E가 모든 소품·건물·주차 차량을 도로 거리장에 대조한다. 도로 위 소품이 1개라도 있으면 실패한다.

### ⑤ 보이는 대부분의 오브젝트는 충돌
- 현황: 건물·랜드마크·일부 놀이 소품은 충돌이 있지만, 나무·가로등·벤치·신호기·무역선 기둥·정원·놀이 소품 대부분(약 13종)은 없다. 충돌 격자는 16u 셀이며 AABB만 지원하고, 차량용 동적 충돌은 전체 순회다.
- 계획:
  - 나무(줄기 반경), 가로등 기둥, 신호기 기둥, 벤치, 표지판, 소화전, 울타리, 놀이 소품, 정원 화단에 작은 충돌체를 붙인다. **소품 목록(`Inst[]`)을 만드는 같은 코드가 충돌을 같이 등록**하게 해서 렌더와 충돌이 어긋나지 않게 한다.
  - 정적 충돌은 수천 개여도 한 번만 격자에 넣으므로 부담이 작다. 차량·NPC 동적 충돌은 근처만 등록한다. 큰 정적 충돌은 청크 단위로 지연 등록한다.
  - 대각 건물은 AABB 조각으로 근사한다(위 8항 위험).
  - 예외: 잔디, 꽃, 도로 표시, 낮은 풀, 낙엽 등 보행에 방해되지 않는 것은 충돌하지 않는다. 걸을 수 있는 소품(벤치 앉기)은 현행 상호작용을 유지한다.
  - 검증: 소품 목록의 99% 이상이 충돌체를 가졌는지 스크립트로 센다. 플레이어·차가 나무·가로등을 통과하지 않는 E2E를 추가한다.

### ⑥ 자연 친화적 도심
- 현황: 가로수는 대로변 몇 그루와 소공원뿐이고 격자 흩뿌림은 거의 안 보인다. 계획된 도심 가장자리 숲 띠는 구현되지 않았다.
- 계획: JSON에 `greenery` 규칙을 둔다.
  - 도로 등급별 가로수 간격(집산·국지는 촘촘하게, 주간선은 중앙분리대 식재), 보도 옆 녹지띠.
  - 구역 용도별 녹지율: 고층 10~15%, 상업 15~20%, 아파트 30%(단지 정원), 주택 40%(마당 나무), 공원 70% 이상.
  - 블록 모서리·건물 뒤 공터에 숲 덩어리(클러스터)를 두고, 윤곽 가장자리와 산악 경계는 숲으로 자연스럽게 이어 붙인다.
  - 나무 종류는 활엽·침엽·화단을 섞고 크기·색을 변화시킨다. 모두 인스턴싱으로 만들고 청크별 거리 LOD를 쓴다. 삼각형 예산은 나무가 늘어도 110k 안에 들도록 청크 LOD와 원경 빌보드로 맞춘다.
  - 에디터에는 "녹지율" 오버레이와 나무 브러시를 둔다. 검증은 구역별 최소 녹지율을 확인한다.

단계 표에 다음을 추가한다.
| I. 실내 연결 | 근접 로딩 실내, 문 개구부, 창문, 외부 어둠, 충돌 개편 | `game/interior.ts`, `render/interior*.ts`, `render/city/building.ts`, `core/terrain.ts` |
| J. 소품·충돌·녹지·주차 | 소품 공통 필터, 충돌체 부착, 녹지 규칙, 실차 주차 | `render/city/props.ts`, `layout.ts`, `systems/vehicle.ts`, `downtown.ts`, `shopstreet.ts` |
순서: I와 J는 C와 병렬로 시작해 E 뒤에 합친다. 실내(I)가 가장 위험하므로 상점·집 1종으로 먼저 시범을 만들고 사용자에게 보여준 뒤 전체로 넓힌다.

## 9. 검증
- `cd client && npx tsc` 무오류.
- 스키마·연결성·시선 축·문 막힘 검증이 시드 JSON에서 통과(에디터 검증 패널과 E2E 양쪽).
- 신규 E2E: JSON 로드 부팅, 폴백 부팅, 대각 도로 위 주행·걷기, 입체교차 오르내림, 길찾기 그래프 연결(crowd), 회전 건물 충돌.
- 기존 도심 관련 spec 전체 통과, 스폰 시야 삼각형 ≤110k.
- 에디터: Playwright로 도로 그리기→검증→JSON 저장→게임에서 로드까지 한 번 통과시키고, 상공 지도 사진(`zz-worldmap`)을 이미지와 나란히 비교한다.

### 10-2. 스키마에서 원본·생성 규칙·확정 배치를 구분하기 — P0

- 2절에는 추가 요구의 `parking`, `greenery`, 높이 프로파일, 실내 문/바닥 정보가 빠져 있다. 필수/선택 필드, 기본값, 단위, 좌표계와 허용 범위를 실제 타입 및 검증 스키마로 정의한다. `rot`의 단위·회전 원점과 기존 `face`의 변환 규칙도 고정한다.
- 중복 ID/잘못된 참조, 유한하지 않은 수치, 길이0인 선분, 폭0 이하, 자기 교차 구역을 검증하고 도로점·배치 개수 상한을 정한다. 스플라인 종류와 샘플링 오차/최대 표본 수도 게임과 에디터가 공유해야 한다.
- `version`을 스키마 버전, 지도 개정, 생성 알고리즘 버전 중 무엇으로 쓰는지 나눈다. 예를 들어 `schemaVersion`, `cityRevision`, `generatorVersion`을 구분하면 생성기 변경과 저장 데이터 이전을 별도로 판단할 수 있다.
- `parcels`의 `t0/t1`이 정규화 매개변수인지 도로 누적거리인지 명시한다. 도로 제어점 삽입만으로 필지가 미끄러지지 않도록 누적거리 기준을 권장한다. 자동 생성 결과를 확정한 뒤에는 수동 수정과 ID를 보존하고, 구역 하나 재생성이 다른 구역을 다시 섞지 않게 한다.
- `bounds`가 **건축 가능한 구역**인지 **실제 섬의 해안선**인지 확정한다. 현재 `heightmap.ts`와 `terrain.ts`는 `CITY_HALF` 사각형을 따로 육지로 인정하므로 JSON polygon만 바꾸면 렌더·물리의 땅이 달라질 수 있다. 지형까지 바꾼다면 높이·native detail·색·표면 분류 마스크를 굽기 전에 같은 source snapshot을 공급한다.

### 10-3. 부팅 경계를 별도 진입점으로 분리하기 — P0

현재 `main.ts`는 `world`, `input`, `loop`, `systems/index`, `debug`를 정적으로 import하고, `state.ts`는 import 중 세이브를 읽는다. 따라서 `main()` 안에서 JSON을 fetch하는 것만으로는 데이터 계산보다 먼저 로드할 수 없다.

- 지도 의존 모듈을 불러오지 않는 가벼운 bootstrap을 두고 **입력 읽기 → 순수 검증 → source 한 번 확정 → 게임 entry 동적 import → 저장 복원 → 월드 구성** 순서를 5절에 명시한다. 스키마/검증의 값 import가 기존 도시·높이 모듈을 역으로 실행하지 않게 한다.
- 배포 JSON과 `?city=local` 편집 초안의 선택 우선순위, localStorage 키/버전, 로딩 제한시간을 정한다. 일반 플레이가 남아 있는 편집 초안을 자동으로 쓰지 않게 한다. URL은 `/steal-an-planet/` 하위 경로에서도 정상이어야 한다.
- 404, 잘못된 JSON, 지원하지 않는 버전, 시간 초과를 구분해 진단을 남긴다. 검증 실패 시 기존 경로로 돌아가더라도 source를 일부만 바꾼 상태는 남기지 않는다. nginx의 JSON 경로에는 `no-cache`뿐 아니라 `try_files ... =404`도 필요하다. 현재 SPA fallback은 없는 JSON에 HTML을200으로 반환할 수 있다.

### 10-4. 입체 도로는 높이와 연결을 별도 데이터로 표현하기 — P0

- 도로 전체의 `grade: 0|1|-1`만으로 램프·교량·지하도와 지형을 따라가는 구간을 표현하기 어렵다. 중심선의 높이 프로파일, 층/표면 ID, 교량·터널 구간과 명시적 램프 연결을 추가한다. 차로 수·실제 폭·주행 방향·보행 허용도 등급 기본값을 개별 구간에서 덮어쓸 수 있게 한다.
- XZ 평면에서 선이 교차한다는 이유만으로 노드를 합치지 않는다. 현재 `citygraph.ts`의 좌표 키는 x/z뿐이다. 새 그래프는 층과 이동 수단을 구분하고, 고가와 지상은 램프를 통해서만 연결해야 한다. 일방통행·회전 제한·보행 금지 구간도 표현해야 한다.
- 다리/산악도로 접속은 위치·폭·높이뿐 아니라 접선 방향과 경사도 함께 검사한다. 구조물 아래 통과 높이는 실제 차량 높이와 비교한다. 데크/물리 등록이 해당 렌더 청크의 생성이나 LOD 변경에 종속되지 않게 한다.

### 10-5. 실내외를 같은 실제 축척으로 전면 재설계하기 — P0

- 사용자 정정: 최종 목표는 **맵을 전면 재설계하면서 외관·실내·사람·차량·도로를 같은 실제 축척으로 새로 맞추는 것**이다. 기존 가상 방의 크기나 기존 건물 발자국을 고수하지 않는다. 기존 기능 보존은 출입·상호작용·소유 ID를 유지한다는 뜻이며 기존 배치를 유지한다는 뜻은 아니다.
- 공통 단위와 사람 키를 기준으로 문·복도·가구·층고·차량·차로 폭을 함께 정하고, 실내 평면과 외벽/창문/문 개구부를 같은 건물 정의에서 생성한다. 실내에 필요한 크기가 나오면 그에 맞게 건물 발자국과 필지도 다시 설계한다.
- `interiorMode: virtual|onsite` 같은 표식은 개발 중 구버전/시험 지도를 구분할 때만 사용한다. 새 지도 출시의 완료 기준은 대상 건물의 실제 위치 실내 전환이며, 가상 방 공존을 최종 목표로 삼지 않는다. 공통 실내 context에는 건물 ID·바닥/층·영역·상호작용·좌표 변환을 둔다.
- 기존 가구 코드의 **좌표만 옮기는 방식은 부족하다.** 현재 작은 집의 방도 최소9u로 확장되므로 실제7×6u 농가 밖으로 가구/벽이 튀어나온다. `floorY`, 내부 유효 영역, 로컬 문 위치·개구 폭/높이, 바닥 두께를 정의하고 가구를 실제 내부 면적에 맞추는 단계가 필요하다.
- 15u/최대2~3채는 로딩 기준의 초기 후보로 두되, 플레이어·NPC가 안에 있는 집과 문 통과 중인 집은 해제하지 않는다. 큰 집 뒤쪽으로 걸어갔다고 실내가 사라지면 안 된다. 창문에서 들여다보는 방과 실제 점유 방의 로딩 우선순위도 나눈다.
- 실제 문도 주차 차량이나 동적 물체에 막힐 수 있으므로 문 앞 여유·통과·닫힘 검사는 유지한다. `nearbyExit`는 가상 방을 지원하는 개발 경로에만 남길 수 있다. 작은 시범 건물은 전체 전환을 검증하기 위한 첫 단계이며, 시범만 완료하고 나머지를 가상 방으로 남겨두는 계획은 아니다.

### 10-6. 충돌·데크의 소유와 해제 API를 먼저 만들기 — P0

- 현재 도시 건물은 전체 발자국이 solid다. 문 렌더에 구멍을 내더라도 이 충돌체를 제거/교체하지 않으면 들어갈 수 없다. 정적 `addSolid()`는 개별 제거 핸들이 없고, `clearDecks()`는 전체 삭제뿐이다. `ownerId`별 등록·교체·해제 계약을 I/J 이전의 선행 단계로 넣는다.
- 전체 건물 충돌 → 문이 열린 벽체/가구 충돌 전환은 원자적으로 처리한다. 렌더 해제, 물리 해제, 플레이어/NPC 점유 여부를 구분한다. 시야 밖이라는 이유만으로 시뮬레이션 중인 차량 앞 충돌을 없애면 안 된다.
- AABB는 넓은 범위 검색에 쓰고, 회전 건물·울타리·문 근처는 OBB/원/캡슐 또는 보수적인 분할의 정확도를 비교한다. AABB 조각 방식과15° 제한을 택한다면 문·보행로가 과도하게 막히지 않는 허용 오차를 정한다.
- “소품99% 충돌 보유” 대신 충돌 필수 종류와 예외 종류를 정의한다. 줄기·기둥·울타리 등 필수 대상은 모두 검증하고, 풀/꽃 같은 예외는 비율의 분모에서 제외한다. 실내/청크를100회 왕복한 뒤 충돌체·데크 수가 누적되지 않는 검사를 추가한다.

### 10-7. 주차 차량의 논리 상태와 화면 로딩을 분리하기 — P0

현재 `removeVeh()`는 메시만 숨기는 함수가 아니라 모션 취소·충돌 제거·`VEH` 목록 삭제까지 한다. 그대로90u 스트리밍에 사용하면 위치·파손 상태의 저장 누락과 도난/재생성 중복이 생길 수 있다.

- `parkingSlotId`와 `vehicleId`를 고정하고, 주차·운전·도난·소유·파손·빈 칸 재생성 시각을 렌더 객체와 별도로 보관한다. 플레이어가 운전/승하차 중인 차량은 거리 기준으로 제거하지 않는다.
- 로딩/해제 거리에는 차이를 두고 최대 활성 상세 차량 수를 정한다. 먼 차를 계속 보여야 한다면 같은 차량 ID의 경량 인스턴스 표현을 사용해 상세 차와 중복으로 보이지 않게 한다. 논리 차량 삭제와 렌더 자원 해제는 별도 API로 만든다.
- 멀어졌다 돌아오기, 도난 후 저장/재접속, 소유차 전환,60초 재생성, 해제 경계에서 왕복하기를 검사한다. 차량 수·상태·재질/지오메트리·충돌체가 누적되거나 복제되지 않아야 한다.

### 10-8. 저장 이전은 부동산 ID뿐 아니라 지도 개정 전체를 다루기 — P0

- `legacyId`를 기록하는 것과 실제 세이브를 이전하는 것은 다르다. `estate.ts`의 수입 계산/목록, 부동산 표시, 앵커 참조에도 같은 alias 해석을 적용한다. 중복 alias와 여러 건물로 갈라지거나 합쳐지는 경우의 정책을 정하고, 이전을 두 번 실행해도 결과가 같게 한다.
- 기존 소유 차량은 저장된 x/z/h를 그대로 복원하므로 새 지도에서는 벽·물속에 놓일 수 있다. `cityRevision` 변화 때 안전한 주차 위치를 재검증한다. 스폰·기지 슬롯·간판·포탈도 앵커 좌표와 함께 이동해야 한다.
- 연결하지 못한 구매 기록은 결정 전까지 보존한다. 고정 경계인 다리 양끝처럼 도시 밖 데이터와 결합된 앵커는 일반 이동 가능 앵커와 구분하고, 위치/높이/방향 제약을 에디터에도 표시한다.

### 10-9. 1u 거리장과 최종 도로 기하의 역할을 나누기 — P1

- 1u 셀 색칠은 지면 분류·미리보기에 재사용하되, 좁은 보도·차선·정확한 소품 제외 경계까지 셀 중심 판정에 맡기지 않는다. 렌더 경계와 충돌·식재 제외는 같은 연속 중심선/폭/높이 표본에서 계산한다.
- 급각의 오프셋 자기 교차, 모서리 miter 길이 제한, 도로 폭 전이, 교차로 포장 폴리곤의 중복과 틈을 정한다. 전역 누적거리 `s`를 공유해 차선 점선·가로등 간격이 청크마다 다시 시작되지 않게 한다.
- “하나의 메시 생성기”는 공통 생성 로직으로 명시하고 출력은 공간 청크별로 유지한다. 도시 전체를 한 Mesh로 합쳐 기존 컬링/LOD를 잃지 않게 한다. 기존 표면 질감의 투영 축척과 팔레트도 같은 규칙으로 유지한다.
- 도로 위 소품 검증에는 중심점뿐 아니라 기둥/줄기/바위의 실제 점유 범위와 높이 층을 사용한다. 차선·횡단보도·고가 상판·신호기 횡지지대처럼 의도된 도로 구조는 장식 소품과 구분한다.

### 10-10. 첫 구현은 작은 구역의 완주로 검증하기 — P0

권장 순서는 **현행 기준 사진/세이브 고정 → 스키마·bootstrap → 작은 시범 지도 → 전체 도심 생성 → 에디터 확장**이다. 첫 시범에는 지상 교차로1개, 서로 연결되지 않는 입체 교차1개와 램프, 회전 집1채·상점1채, 주차칸1개를 넣는다. 이 구역에서 걷기·운전·출입·저장/재로드·스트리밍 해제를 끝까지 통과한 뒤 확장한다.

7절의 C/D/E/I/J는 현재 파일 소유가 겹친다. C의 `render/city/*` 포괄 소유를 없애고 다음을 파일 단위로 지정하는 편이 안전하다.

| 공용 지점 | 단일 편집 책임과 다른 담당의 사용 방식 |
|---|---|
| 도로 표본/높이/접속 API | B/D가 계약을 공동 설계하되 파일별 편집자는1명. C/E/J는 같은 확정 표본을 소비 |
| `building.ts`, 실내 개구부 | C/I 중1명만 편집, 외관·실내 모듈의 입력/출력 계약으로 분리 |
| `layout.ts`, `props.ts` | C/J 중1명만 편집, 소품 배치가 공통 도로 점유 검사를 호출 |
| `vehicle.ts` | E가 논리 차량/저장 책임, J는 주차칸 데이터와 렌더 활성화 요청만 전달 |
| `core/terrain.ts`, `core/deck.ts` | 충돌/바닥 API 담당1명, I/J/D는 소유 핸들을 통해 등록/해제 |

### 10-11. 완료 기준에 실제 배포·화면·경계 사례를 추가하기 — P1

- 에디터 localStorage 미리보기 성공과 배포 JSON 성공을 분리한다. **다운로드 → 깨끗한 브라우저에서 해당 파일로 부팅 → 같은 ID/배치 해시 확인**을 필수 왕복 검사로 넣는다. `/`와 `/steal-an-planet/` 양쪽 및 누락/잘못된 JSON 폴백을 검사한다.
- 도로 끝점 검사는 이동 수단별로 나눈다. 고속도로 전체를 보행 그래프에 넣지 말고, 차량 연결성과 허용된 보도/횡단보도 연결성을 각각 검사한다. 같은 XZ의 고가/지상에 허위 그래프 간선이 없는지도 확인한다.
- 고정 카메라·시간·LOD 조건에서 스폰뿐 아니라 복잡한 교차로, 주차장, 실내2~3채와 바깥이 함께 보이는 장면을 측정한다. 화면 삼각형, calls, 충돌 후보 수/처리 시간, 로드 지연과 반복 이동 후 메모리를 함께 기록한다. 에디터의 전체 배치 추정치만으로 성능 통과를 판정하지 않는다.
- 원본 참조 이미지의 실제 파일 경로와 비교 카메라를 문서에 명시한다. 상공 배치도 외에 지상 시야·도시 외곽·스카이라인·교차로·문 앞을 같은 조건으로 비교한다. 녹지율은 수관 투영인지 지표 면적인지, 도로/건물/물 면적을 어떻게 제외하는지 정의한다. 도로 위계가 맞는 것과 자연스러운 도시로 보이는 것을 별도 완료 기준으로 둔다.

**우선 적용 권장:** 현황/95k 기준 정정 → bootstrap과 스키마 확정 → 충돌 소유·해제 API → 작은 실제 위치 실내/입체 도로 시범 → 주차 상태 분리. 이 순서로 선행 위험을 줄인 뒤 도시 전체와 에디터 도구를 확장하는 것이 좋다.

## 11. 사용자 방향 보완: JSON을 빌드하는 도시 생성기 (2026-11-06)

사용자가 제안한 방향은 **AI가 가로수·벤치·가로등의 좌표를 하나씩 작성하는 대신, 도로망과 규칙을 JSON으로 정의하고 빌드하면 고정 구조물이 알고리즘으로 생성되는 방식**이다. 이를 새 도시의 기본 제작 방식으로 삼는다. AI/사람은 도시 구조·용도·도로 단면·스타일과 예외를 설계하고, 반복 배치는 생성 코드가 맡는다.

### 11-1. 원본과 빌드 결과

```text
city.source.json + 도로/소품 프로필 + 에셋 치수
  → 축척·참조 검증
  → 중심선·높이·교차로 계산
  → 차도·보도·필지·실내외 건물 생성
  → 배치 가능한 보도/녹지 구간 계산
  → 가로등·가로수·벤치·표지판 자동 배치
  → 도로 침범·통행·충돌·예산 검증
  → city.compiled.json + 공간 청크/인스턴스·충돌·길찾기 데이터
```

- 원본에는 도로 연결·곡선·폭/단면 프로필, 구역 용도, 건물의 실내외 치수, 앵커와 배치 규칙을 저장한다. 생성 가능한 소품의 수천 개 좌표는 기본 편집 대상에서 제외한다.
- 빌드 결과에는 실제 표본·교차로 포장·배치 변환·재질/에셋 참조·충돌체·그래프를 담는다. 렌더·보행·충돌이 서로 좌표를 다시 추측하지 않는다.
- 에디터 미리보기와 배포용 빌드는 같은 생성 라이브러리를 사용한다. 게임은 검증된 결과를 읽어 청크별로 로드하며, 복잡한 교차로 계산과 배치 탐색을 매 프레임 실행하지 않는다. 파일명은 설계 예시이며 기존 `city.json` 로딩 계획과 함께 정리한다.

### 11-2. 폭과 단면에 따른 배치

도로 등급만으로 위치를 결정하지 않고 **차도·중앙분리대·주차대·보도·식재대의 실제 폭**을 사용한다.

| 구조물 | 배치 알고리즘의 입력과 판단 |
|---|---|
| 가로등 | 도로 단면·스타일에서 한쪽/양쪽/엇갈림/중앙 배치와 목표 간격 선택. 보행 유효 폭을 남기는 위치에 기둥 배치 |
| 가로수 | 식재대 폭·수종의 성목 크기·건물/문/차도 여유를 검사. 들어갈 공간이 없는 구간에는 강제로 심지 않음 |
| 벤치 | 넓은 보도·공원 접면·쉼터 구간을 선택하고 앉는 공간과 통행 공간을 함께 확보. 프로필에 따라 방향 결정 |
| 신호기·표지판 | 교차로 접근 방향·정지선·횡단보도·시야 확보 구간에서 위치 결정 |
| 건물 출입·차량 진입부 | 실제 문·계단·경사로·주차장 진출입 폭을 예약하고 다른 소품의 배치 금지 영역으로 사용 |

규칙은 프로필로 관리한다. 예를 들어 도로를 넓혀도 배치 코드에 좌표를 다시 적지 않고, 보도/식재대 경계와 관련 구조물 위치가 다시 계산된다.

### 11-3. 전체 길이를 고려한 유동적인 간격

1. 도로 중심선을 누적거리로 표본화하고, 같은 도로가 편집용 선분/렌더 청크로 나뉘어도 하나의 거리 기준을 유지한다.
2. 교차로 모서리·횡단보도·정류장·건물 문·차량 진출입부 등에서 필요한 여유를 빼서 배치 가능한 연속 구간을 얻는다.
3. 각 구간의 길이와 목표 간격으로 배치 개수를 정한다. 남는 길이는 양 끝 여유와 간격에 나눠 배분하되 프로필의 최소/최대 간격을 지킨다. 마지막에만 짧은 간격이 몰리지 않게 한다.
4. 여러 종류의 소품을 함께 조정한다. 필요한 교통 시설과 통행 공간을 우선 확보하고 가로등·나무·벤치는 허용된 범위에서 위치를 옮기거나 생략한다. 탐색 횟수에는 상한을 둔다.
5. 최종 에셋 점유 범위·높이 층으로 충돌/침범을 검사한다. 배치할 수 없으면 이유를 에디터에 표시한다. 좌표를 임의로 밀어 차도나 문 앞에 놓고 성공으로 처리하지 않는다.

교차로에서는 먼저 회전 구간과 포장/보도 경계를 완성한 뒤 각 접근 도로의 소품 배치를 잘라낸다. 선분마다 독립적으로 가로등을 찍어서 교차로 한쪽에 기둥이 몰리는 방식을 피한다.

### 11-4. 재현·수정·성능

- 같은 원본·seed·생성기/에셋 프로필 버전이면 같은 결과가 나와야 한다. 수종·색·크기의 변화도 안전 범위 안에서 seed로 생성한다.
- 수정한 도로와 연결 교차로, 영향을 받은 필지/주변 구간만 다시 빌드한다. 무관한 구역의 소품과 ID가 다시 섞이지 않게 한다. 수동 예외는 원본의 금지 구간/고정 위치/스타일 덮어쓰기로 저장하고 다음 빌드에도 유지한다.
- 생성 결과를 사람이 직접 수정한 뒤 재빌드 때 잃어버리는 흐름은 피한다. 에디터에서의 수정은 원본 구조나 명시적 예외로 되돌려 기록한다.
- 알고리즘 생성은 AI가 작성할 반복 좌표와 수정 토큰을 줄이고 배치 일관성을 높인다. 실제 GPU 비용은 생성 방식만으로 줄지 않으므로 인스턴싱·공유 재질·청크 컬링·LOD·활성 충돌 수의 예산은 계속 적용한다.
- 완료 검사는 도로 폭/길이/교차각을 바꾼 뒤 재빌드했을 때도 **도로 침범0·문/진출입 통행 유지·간격 허용 범위·출력 재현성**을 만족하는지 확인하는 방식으로 추가한다.

### 12-2. 도시 생성기 구조 (2절·4절·6절 대체)
```
city.source.json  (사람/AI가 편집: 도로 연결·곡선·단면 프로필, 구역 용도, 건물 치수·실내 정의, 앵커, 배치 규칙·예외)
   └─ citygen 빌더 (client/src/citygen/*, 게임·에디터·Node CLI 공용)
        축척·참조 검증 → 중심선·높이·교차로 → 차도·보도·필지 → 건물(외관+실내)
        → 배치 가능 구간 계산 → 가로등·가로수·벤치·표지판 자동 배치 → 침범·통행·충돌·예산 검증
   └─ city.compiled.json (빌드 결과: 표본·포장·배치 변환·에셋 참조·충돌체·그래프. 게임은 이것을 읽음)
```
- 소품 좌표를 AI가 쓰지 않는다. 사람/AI는 구조·용도·단면·스타일·예외만 편집한다. 에디터 수정은 **원본 구조 또는 명시 예외**(금지 구간·고정 위치·스타일 덮어쓰기)로 저장해 재빌드 때 잃지 않는다.
- 배치는 **도로 단면(차도·중앙분리대·주차대·보도·식재대 폭)**과 누적거리 `s` 기반: 배치 가능 연속 구간 → 목표 간격으로 개수 결정 → 남는 길이를 끝 여유와 간격에 분배(최소/최대 간격 준수) → 소품 종류 간 우선순위 조정(교통 시설 우선, 나무·벤치는 이동·생략) → 점유 범위·높이 층으로 침범 검사. 배치 불가면 사유를 에디터에 표시하고 임의로 밀어 넣지 않는다. 교차로는 포장·보도 경계를 먼저 만든 뒤 접근 도로 배치를 잘라낸다.
- 재현성: 원본 + seed + `generatorVersion` + 에셋 프로필이 같으면 결과가 같다. 수정 시 영향 구간(도로·연결 교차로·인접 필지)만 재빌드하고 무관 구역의 소품·ID는 유지.
- 건물 ID는 원본에 명시(필지 ID에서 안정적으로 파생)해 세이브 호환을 지킨다. 앞서 말한 "건물 확정(bake)"은 원본의 `buildings`가 맡고, 소품 같은 반복물만 빌더가 생성한다.
- 정점 AO·소품 글로우·도로 젖음(그래픽 계획 `GRAPHICS_PLAN.md`)은 이 빌드 결과를 입력으로 쓰는 후속 단계다.
- 성능은 생성 방식이 아니라 인스턴싱·공유 재질·청크 컬링·LOD·활성 충돌 수로 지킨다(95k 기준 유지).

### 13-2. 높이 데이터 설계
- 범위: **도시 섬만** JSON을 쓴다. 시골 섬(`wild-height.ts`)과 12개 행성 섬은 지금처럼 절차 생성한다.
- 원본(`city.source.json`): 현재 도시 섬 높이(`heightmap.ts` + `belt-height.ts`)를 오프라인 도구로 굽고 다듬은 **5u 격자**(고도 cm 정수, 델타 인코딩 + base64). 도시 섬 범위 약 11만 칸, 압축 후 수백 KB.
- 다듬기 도구(`tools/terrain-bake.mjs`): 계단 얼룩(5u 격자) 완화, 곧은 벽 같은 능선 침식·곡률 보정, 가우시안 평활. **해안·낭떠러지(`CLIFF1~3`) 경계와 다리 접속부는 보존**한다. 전후를 `zz-worldmap` 상공 사진과 지상 스크린샷으로 비교한다.
- 편집 레이어 `terrain.edits`: 평탄화 패드(앵커·필지·경기장·포탈 광장), 도로 절토·성토 회랑, 언덕 브러시(올리기·내리기·평탄화·부드럽게)를 원본에 저장하고 빌더가 적용한다.
- 컴파일 결과: 최종 높이 래스터(도로·패드 반영), 경사·표면 분류 마스크, 도시 경계 다각형 질의. 게임은 기존 지형 LOD(2.5u/5u/10u, `render/terrain.ts`)와 `groundH`를 그대로 쓰고 **높이 공급원만 JSON으로 바꾼다**(`heightmap.ts`의 도시 영역).
- 옛 절차 코드(`belt-height.ts` 능선 목록, `mountain-road.ts` 등)는 구 도심 보관본으로 옮기고, 산악도로·천문대·철탑은 JSON 도로·앵커로 재정의한다.

### 13-3. 지형 규칙
- **경사 한도**: 건물 필지 12% 이하, 도로는 국지 10% / 집산·보조간선 8% / 주간선 8% / 고속 6% 이하(시범에서 값 조정). 한도를 넘는 곳은 절토·성토 단과 옹벽, 지그재그 도로, 숲·공원으로 처리한다.
- **건축 상한 고도**: 낮은 산자락까지(초안 해발 30~40u). 빌더가 상한 위·한도 초과 경사 구역에는 필지를 만들지 않는다.
- **필지 대지**: 필지마다 평탄한 대지를 만들고, 건물·실내 `floorY`·소품·주차칸·길찾기 노드는 그 높이를 쓴다. 경기장 구장, 포탈 광장, 다리 접속로는 앵커의 평탄화 반경으로 평지를 만든다.
- **사과 시선 축**(기지 (0,17), 정북 ±8°, 고도 8°): 이 축을 가리는 높이·건물은 빌더가 거부한다. 북쪽 구간은 축 아래에서만 올린다.
- 다리 끝과 산악도로 시작점은 위치·폭·높이·접선·경사를 새 지형과 어긋나지 않게 검사한다.

### 13-4. 렌더·시스템 변화 (평지 가정 제거)
지금 도심 땅은 1u 셀로 색칠한 평평한 판이고 모든 것이 y=0/0.06 가정이다. 비탈 도시를 위해 아래를 바꾼다.
- **땅**: 도심도 지형 메시(LOD)로 그린다. 도로·보도·중앙선·횡단보도는 **지형에 얹힌 리본 메시**(공간 청크별 출력)로 그리고, 그 밑 지형은 도로 높이에 맞춰 평탄화·어깨 경사를 둔다. 1u 셀 색칠은 지면 분류·미리보기에만 쓴다.
- **y 인지**: 건물 바닥, 소품(가로등·나무·벤치), 주차 차량, 실내 `floorY`, 길찾기 노드(`x,z,layer`에 y 추가), NPC·차량 주행이 모두 `groundH`에서 y를 얻는다. 차량은 시골 섬·산악도로의 기존 경사 주행 코드를 재사용해 도심 밀도에서 검증한다.
- **도시 경계**: `CITY_HALF`를 쓰는 곳(무역선 기둥 `tradeline.ts`, 경찰 `inCity`, 폰 지도, 지면 마스크 `terrain.ts`, 군중, 소품·건물 클램프)을 `inCity(x,z)`(JSON 경계 다각형)와 `cityBounds`로 바꾼다. 무역선 기둥은 새 경계를 따라 놓는다.
- **세이브 보호**: 모르는 건물 ID 무시, 소유 차량 위치 재배치만 한다.

### 13-6. 추가 검증
- 높이 JSON 로드 후 같은 좌표의 `groundH`가 다듬기 허용 오차(예: 0.5u) 안에 있고, 해안·낭떠러지·다리 접속부는 동일하다.
